## Concrete families, in ascending implementation cost

1. Rust TLS certificate/hostname verification bypass. `reqwest` ClientBuilder `(tls_)?danger_accept_invalid_certs(true)` / `(tls_)?danger_accept_invalid_hostnames(true)`; native_tls methods similarly. Require library/receiver context, literal true, exclude test/example/fixture/comment/string appearances. Official current reqwest docs expose both new `tls_` prefixes and deprecated old names: https://docs.rs/reqwest/latest/reqwest/struct.ClientBuilder.html . Narrow, high-confidence configuration defect, not injection.
2. C/C++ TLS bypass. `curl_easy_setopt(handle, CURLOPT_SSL_VERIFYPEER, 0L)` / `CURLOPT_SSL_VERIFYHOST, 0L`; explicit zero only, require curl function not arbitrary matching constant prose. https://curl.se/libcurl/c/CURLOPT_SSL_VERIFYPEER.html explains MITM risk and default 1. OpenSSL SSL_VERIFY_NONE needs client/server context to avoid falsely flagging servers that simply do not require client certificates.
3. C gets(buffer) is inherently unbounded, unlike strcpy which requires bounds/dataflow. Require real call tokens, not declarations/custom functions/comments; start medium until labelled. Generic nonliteral printf requires demonstrated input flow before high confidence; do not use blanket strcpy/rand/unsafe as high-confidence security signals.
4. Scala Play request-to-SQL and command shell flow. Semgrep tainted-sql-from-http-request and tainted-slick-sqli are HIGH; generic dangerous-shell-run is LOW. Require visible HTTP input linked to `s"SELECT ... $x"` raw SQL sink or `Seq("sh","-c",x).!`; do not flag harmless Seq("cmd",arg) as shell injection.
5. Scala Slick: **sql"...$value" binds parameters and is safe**. Raw `#$value` splices literal SQL. Only raw splicing/overrideSql with demonstrable request input is a strong injection claim. Official source https://scala-slick.org/doc/3.3.3/sql.html#splicing-literal-values . Play Html(request...) is likewise a candidate if raw response dataflow confirmed.
