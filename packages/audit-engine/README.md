# auditscout

Инструмент для выбора аудит-конкурса. Строился как фаза 0 сканера уязвимостей
и по дороге отменил остальные фазы — измерением.

## Запуск

```
d:\polymarket\.venv\Scripts\python.exe contests.py            # вердикт
d:\polymarket\.venv\Scripts\python.exe contests.py --history  # теснота по годам и языкам
d:\polymarket\.venv\Scripts\python.exe contests.py --top      # конкурсы поимённо
```

Нужен только `httpx`. Ключей не требует, ничего не отправляет, всё скачанное
кэширует в `data/cache` — завершённый конкурс не меняется, качать его дважды
незачем.

## Источники

**Sherlock.** Список `mainnet-contest.sherlock.xyz/contests` бедный, но у
каждого конкурса есть детальная карточка `/contests/{id}`, и вот в ней всё
нужное: `nsloc`, `scope` с репозиторием, коммитом и построчной разбивкой по
файлам, `num_competition_issues`, `requires_kyc`, `rewards_tiers` и полный
текст отчёта о находках. 301 конкурс.

**Cantina.** `cantina.xyz/api/v0/competitions` отдаёт всё одним запросом, но
без scope и без размера кода. Детальная карточка закрыта, отвечает 404.
143 соревнования.

Code4rena публичного API не имеет (все варианты дают 404), CodeHawks требует
ключ, у Hats домен API не отвечает. У Solodit открытого API нет — но он и не
нужен, отчёты Sherlock приходят прямо из API.

**Immunefi открыт** (проверено 16.08.2026): `immunefi.com/public-api/
bounties.json` — 248 программ со ВСЕМ скоупом, 6083 актива-контракта, шесть
мегабайт, без ключа. Раньше здесь стояло «закрыт» — это была неверная ссылка.

## Каталог баунти всего мира: market.py

```
python market.py --refresh        перекачать снимок и показать, что изменилось
python market.py --diff           дифф без перекачки
python market.py                  смарт-контрактные программы, по тесноте
python market.py --all            плюс веб и приложения
python market.py --repos          только с публичным GitHub в скоупе
python market.py --id <имя>       карточка: скоуп, репозитории, что запускать
python market.py --scopes <сайт>  дотянуть скоупы (нужно для плотности)
python market.py --refresh        перекачать снимок data/market.json
```

Девять площадок в одном формате: immunefi, hackerone, bugcrowd, standoff365
(СНГ), intigriti, hackenproof, yeswehack, cantina, sherlock. Всего 1488 живых
программ. Полный разбор — что каждая отдаёт, что закрыто и как обстоит с
доступом из Казахстана — в [data/PLATFORMS.md](data/PLATFORMS.md).

## Свежесть: дифф вместо перечитывания

`--refresh` кладёт прошлый снимок в `data/market_prev.json` и печатает
производную: НОВЫЕ программы (у них плотность минимальна по построению и это
состояние живёт дни), выросший скоуп, исчезнувшие, теснеющие.

По выбранным мишеням есть проверка дешевле полного обхода:

```
python targets.py --check
```

Сверяет выбранное со снимком (жива ли программа, не изменились ли комиссия и
KYC, не выросло ли число заявок) и спрашивает у GitHub `pushed_at` по каждому
репозиторию скоупа — свежесть кода и метку «архив».

## Выбор мишеней и работа по ним: targets.py

```
python targets.py --pick --repos   мультивыбор из рынка: «1,4,7» или «1-5»
python targets.py                  что выбрано и в каком состоянии
python targets.py --prep <имя>     папка, BRIEF.md, исходники, адреса
python targets.py --scan <имя>     прогнать все сигналы, сложить в файлы
```

Мишени берутся с любых площадок вперемешку и живут в `data/targets.json`.
Рабочая папка — `data/bounty/<slug>/`: `BRIEF.md` (скоуп, адреса, репо,
порядок работы), `src/` (скачанные деревья), `signals/*.txt` (вывод
`audits`, `blindspots`, `recodiff` по репозиторию и `siblings`, `statesync`
по дереву — целиком, чтобы читать заходами и вычёркивать).

## Главное про единицы

`num_competition_issues` и `totalFindings` — это **поданные заявки**, а не
принятые уникальные находки. Проверено сверкой со списком issue в отчёте: у
`2024-11-autonomint` 1066 заявок против 75 уникальных проблем, то есть каждую
в среднем нашли 14 человек.

Для оценки это удача. Награда за проблему делится между всеми, кто её подал,
значит

```
фонд / число заявок  ≈  ожидаемая выплата за одну твою заявку
```

Называть это «доллар на находку» неверно — правильно «доллар на заявку».

### Но $38 — это медиана по мусору

Число выше считалось по всем поданным заявкам, включая невалидные и дубликаты.
По **валидным** находкам картина другая. Разобрано 120 отчётов Sherlock,
1474 проблемы:

| уровень | проблем | медиана нашедших | нашёл ровно один | медиана выплаты |
|---|---|---|---|---|
| High | 500 | 4 | **23%** | **639$** |
| Medium | 966 | 3 | **34%** | **388$** |

Главное здесь не деньги, а последняя колонка. Треть валидных Medium и почти

Выплата считается по весовой сетке Sherlock (High 5, Medium 1): доля фонда на
проблему, делённая на число нашедших.

## Что не сработало

Первая версия предсказывала число заявок регрессией по размеру кода и величине
фонда. На 398 конкурсах:

| признаки | R² |
|---|---|
| только фонд | 0.000 |
| фонд + площадка | 0.003 |
| фонд + площадка + срок | 0.059 |
| фонд + размер кода | 0.081 |
| фонд + площадка + год | 0.108 |

**Размер фонда не предсказывает тесноту вообще** — коэффициент −0.01. Крупный
фонд не собирает больше участников: приходят одни и те же люди на всё подряд.
Единственный признак с какой-то силой — год, и он перекрывает остальное.
Регрессия выброшена, прогноз строится по базовой ставке года (`rank.Baseline`).

## Корпус находок: что пропускают остальные

`corpus.py`, работает офлайн по кэшу. Разобрано 2937 находок из 235 конкурсов
и разложено по классам. Колонка «одиночек» — доля находок, которые подал ровно
один человек, то есть за которые не пришлось делиться.

| класс | находок | одиночек | мед. выплата |
|---|---|---|---|
| реентранси | 20 | 45% | 787 |
| округление | 101 | 44% | 780 |
| оракул и цена | 170 | 43% | 889 |
| учёт | 220 | 41% | 763 |
| ликвидация | 231 | 41% | 722 |
| комиссия | 257 | 40% | 639 |
| мостовое/кросс | 68 | 35% | **1 142** |
| слippage | 99 | 32% | 629 |
| инициализация | 37 | 30% | 454 |
| доступ | 48 | 27% | 468 |
| **токен нестандарт** | 41 | **27%** | **170** |

Читается однозначно и прямо отвечает на вопрос про сканер: **классы, которые
ловит автоматика, стоят внизу таблицы по обоим показателям.** Нестандартные
токены (fee-on-transfer, USDT, ребейз), контроль доступа, инициализация прокси —
это чек-лист у каждого участника, доля одиночек минимальная, выплата тоже.
Платят за понимание логики протокола: округление в контексте, учёт, ликвидации,
цена оракула.

То же по словам заголовка (счёт по конкурсам, не по находкам — иначе один
протокол с девятью находками одного человека забивает верх): у одиночек
`liquidator` 3.1, `rounding` 2.6, `curve` 2.5; у массовых `usdt` 0.3,
`division` 0.3, `functions` 0.3, `anyone` 0.4.

## Карта репозитория и её проверка

`recon.py` тянет из API точный список файлов в скоупе с коммитом, клонирует
(с фолбэком на зеркало `sherlock-audit` — заказчики закрывают репозитории
после конкурса) и переводит объём в часы чтения.

Ранжирование файлов по признакам **проверено и не подтвердилось.**
`validate.py` на 106 конкурсах и 1575 находках:

| доля находок в первых K файлах | K=3 | K=5 | K=10 | K=15 |
|---|---|---|---|---|
| по весу признаков | 51% | 62% | 77% | 83% |
| просто по размеру файла | **53%** | **65%** | **82%** | **88%** |
| случайно | 22% | 34% | 51% | 65% |

Веса, переобученные по измеренному лифту и проверенные на отложенных
конкурсах, на малом бюджете тоже проигрывают размеру (28% против 30% при 10%
строк) и выходят вперёд только к 30–50% прочитанного — а такой бюджет на
конкурсе недостижим.

Причина не в признаках, а в гранулярности: в большом файле больше всего,
поэтому размер уже несёт ту же информацию. Поэтому файловый вид сортируется по
размеру, а признаки показываются как пометки «что внутри».

## Уровень функций: здесь ранжирование заработало

Файловая гранулярность оказалась просто слишком грубой. 91% находок (2761 из
3023) содержат пермалинк с номером строки, а значит разметку можно сделать по
функциям, а не по файлам. `validate.py --test funcs`, **141 конкурс,
27 750 функций**, из них 9% задеты находками:

| признак | задето | без признака | лифт |
|---|---|---|---|
| деньги | 25% | 8% | **3.07** |
| реентранси | 22% | 9% | 2.54 |
| математика | 18% | 9% | 2.06 |
| цикл | 18% | 9% | 2.04 |
| оракул | 16% | 9% | 1.85 |
| подпись | 13% | 9% | 1.37 |
| ассемблер | 6% | 9% | 0.64 |
| внешний вызов | 6% | 9% | 0.59 |
| **доступ** | **6%** | 10% | **0.58** |
| обновляемость | 4% | 10% | 0.37 |

**Главное здесь — инверсия.** На файлах контроль доступа давал лифт 1.78, на
функциях — 0.58. Функция с `onlyOwner` содержит находку вдвое реже средней.
Противоречия нет: файлы с контролем доступа это крупные важные файлы, отсюда
файловая корреляция; но сама защищённая функция — админский вызов, куда
посторонний не дотянется. То же говорит корпус независимо: класс «доступ» там
27% одиночек и 468$ медианы.

Прямая проверка этой мысли:

| класс функции | функций | задето находками |
|---|---|---|
| **беспермиссионная + деньги** | 1212 | **29%** |
| защищённая + деньги | 942 | 20% |
| беспермиссионная, без денег | 11954 | 9% |
| защищённая, без денег | 13642 | 8% |

При базовой ставке 9%. **Беспермиссионные функции, двигающие деньги, — это 4%
функций с тройной плотностью находок.** Это и есть правило, ради которого всё
строилось, и `recon.py` теперь сортирует по нему.

Покрытие при бюджете в строках, веса обучены на половине конкурсов и
применены к другой:

| прочитано | по признакам | по размеру | случайно |
|---|---|---|---|
| 5% | 7% | 6% | 6% |
| 10% | **12%** | 9% | 10% |
| 20% | **25%** | 20% | 19% |
| 30% | **36%** | 32% | 29% |
| 50% | **57%** | 51% | 48% |

Выборка выросла с 88 конкурсов до 141, и числа почти не сдвинулись — это и
есть признак, что результат настоящий, а не подгонка под шум.

Выигрыш устойчивый, но скромный: примерно четверть-треть относительно базовой
линии. Это не «80% находок за 20% кода», и обещать такое нечестно.

### Ошибка разбора, которую пришлось чинить

Первая версия искала заголовки функций регуляркой по сырому тексту и ловила
комментарии: `// function to withdraw` становился функцией с именем `to`, а
дальше по скобкам к ней приклеивалось «тело» на 481 строку. На одном конкурсе
это раздувало счёт с 3792 строк до 5531. Исправлено маскированием комментариев
и строковых литералов (`recon.mask`); все числа выше пересчитаны после починки.

## Холодные признаки: математика учёта

Проба на завершённом конкурсе (`practice.py`, 2025-02-yieldoor) вскрыла
именованную слепую зону. Из семи одиночных находок три сидели в
internal-функциях вспомогательных библиотек — `ReserveLogic`,
`InterestRateUtils`, — где нет ни денег, ни границы доверия, ни внешних
вызовов, то есть ни одного горячего признака.

Пример, ради которого добавлен второй список (`ReserveLogic:150-163`):

```solidity
newTotalBorrows = newIndex * totalBorrows / oldIndex;   // может округлиться в 0
...
reserve.lastUpdateTimestamp = block.timestamp;          // но время идёт всегда
```

Ошибку эксплуатирует не атакующий, а само время. Признаки здесь другие, и
измерены они на 13 994 холодных функциях 141 конкурса при базовой ставке 8%:

| холодный признак | функций | задето | без признака | лифт |
|---|---|---|---|---|
| **накопитель** | 66 | 33% | 8% | **4.44** |
| метка времени | 274 | 26% | 7% | 3.62 |
| необязательная запись | 386 | 24% | 7% | 3.33 |
| доля от общего | 99 | 23% | 8% | 3.09 |
| деление до умножения | 217 | 23% | 7% | 3.06 |
| ставка за период | 104 | 21% | 8% | 2.81 |
| масштаб | 447 | 17% | 7% | 2.36 |
| приведение вниз | 494 | 14% | 7% | 1.95 |

**4.44 у накопителя — самый высокий лифт за весь проект**, горячие давали
максимум 3.07. И покрытие внутри своей подвыборки лучше:

| прочитано | холодные признаки | по размеру | случайно |
|---|---|---|---|
| 10% | **16%** | 8% | 9% |
| 20% | **26%** | 18% | 20% |
| 30% | **38%** | 30% | 32% |

Вдвое против базовой линии, тогда как горячие давали 1.33 раза.

Две шкалы не складываются напрямую и применяются раздельно: горячие лифты
мерились на всех функциях, холодные — только на холодных, где своя базовая
ставка. Холодные веса применяются лишь к холодным функциям.

Проверка замкнулась: после этой правки `recon.py --contest 791` ставит
`_updateIndexes` на первое место, а `latestBorrowingIndex` на второе — ровно
те две функции, из которых состоит пропущенная находка M-2.

## Справочник по типам протоколов

`protocols.py`, офлайн. Четыре пробы на завершённых конкурсах (`practice.py`)
дали 3 находки из 42 и показали, что провал не в поиске файлов, а в
предметной области. Общие руководства это не закрывают: они перечисляют
классы багов, а нужно знать, что ломается в конкретном типе протокола.

Поэтому справочник собран не из статей, а из 2937 находок 235 отчётов, где
у каждой известны уровень, число нашедших и доля фонда. Метрика — доля
одиночек: чем выше, тем меньше людей вообще доходит до темы.

| тип | конкурсов | одиночек | медиана у одиночек |
|---|---|---|---|
| **мост / кросс-чейн** | 5 | **52%** | **5 714$** |
| рестейкинг | 4 | 12% | **8 000$** |
| перпы | 9 | 47% | 1 750$ |
| AMM/DEX | 14 | 20% | 2 098$ |
| стейкинг | 87 | 40% | 1 549$ |
| кредит | 42 | 40% | 1 185$ |
| хранилище | 23 | 38% | 892$ |

**ИСПРАВЛЕНО ИЗМЕРЕНИЕМ.** Первая редакция объявляла мосты «самой незанятой
темой» — 52% одиночек. Это артефакт выборки: классификатор по названию нашёл
всего 5 мостовых конкурсов. Поиск кросс-чейна по СОДЕРЖАНИЮ находок даёт 14
конкурсов и 381 находку, и картина переворачивается:

| | кросс-чейн (14 конкурсов) | остальной корпус |
|---|---|---|
| одиночек | **33%** | **37%** |
| медиана выплаты | 463$ | 614$ |
| медиана у одиночек | **1 803$** | 1 364$ |

Доля одиночек не выше, а ниже базовой. Выживает одно преимущество: одиночная
находка в кросс-чейне платит на 32% больше. Реально, но это не «вдвое меньше
конкурентов».

Проверка утверждений литературы (газовый грифинг, повтор, батчинг) на той же
расширенной выборке оставляет один механизм:

| механизм | концентрация | одиночек | медиана | набл. |
|---|---|---|---|---|
| **повтор / nonce** | **3.2x** | **60%** | **3 103$** | ~11 |
| газовый бюджет | 1.8x | 39% | 902$ | ~34 |
| порядок / батч | **0.6x** | 77% | 13 208$ | ~11 |

Порядок и батчинг в кросс-чейне встречаются РЕЖЕ, чем в остальном корпусе.
Высокие выплаты стоят на трёх-четырёх наблюдениях — шум.

Урок тот же, что и по всему проекту: эдж на выборке из пяти наблюдений
исчезает при её расширении.

## Что предсказывает тесноту на самом деле

Тип протокола не предсказывает ничего. Предсказывает **плотность покрытия** —
заявок на строку кода в скоупе. Корреляция с долей одиночных находок
**r = −0.67**, сильнее любого отдельного признака: размер кода +0.41, число
заявок −0.53, срок +0.24, размер фонда +0.20. 193 конкурса.

| плотность | заявок | строк | одиночек | $ одиночке |
|---|---|---|---|---|
| 0.021 | 70 | 3516 | **67%** | 2 286$ |
| 0.073 | 137 | 2190 | 36% | 2 098$ |
| 0.145 | 225 | 1570 | 17% | 1 211$ |
| 0.257 | 309 | 1072 | 15% | 1 469$ |
| 0.636 | 615 | 639 | **0%** | 561$ |

Механизм простой: двести человек вычищают тысячу строк целиком, и уникальных
находок не остаётся вовсе. Углы, куда никто не дошёл, бывают только в большом
коде.

### Бэктест правила отбора

Только на информации, доступной ДО входа. Отбор верхней четверти из 193
конкурсов:

| правило | одиночек | $ на находку |
|---|---|---|
| без отбора | 20% | 1 084$ |
| **по размеру скоупа** | **43%** | **1 885$** |
| по размеру фонда | 33% | 2 067$ |
| по фонду на строку | **5%** | 1 486$ |
| мелкий скоуп | **0%** | 998$ |

**Брать самый крупный скоуп, какой успеваешь.** Удваивает шанс быть
единственным нашедшим и вдвое поднимает выплату: за 48 конкурсов при одной
находке в каждом 192 036$ против 73 550$ у мелкого скоупа.

Два отрицательных результата, оба против интуиции: правило «начни с
маленького, чтобы охватить целиком» даёт **0% одиночек**, а «фонд на строку»
— метрика, которая выглядит разумной мерой ценности, — даёт 5% и работает
хуже, чем не отбирать вовсе.

### Проверка на отложенных годах

Правило выведено на всём корпусе сразу — это подгонка. Честная проверка:
порог берётся по 2022–2024 (медиана плотности 0.115) и применяется вслепую
к 2025–2026.

| поздние годы | конкурсов | одиночек | $ на находку |
|---|---|---|---|
| плотность ≤ 0.115 | 7 | **56%** | **2 560$** |
| плотность > 0.115 | 36 | **0%** | 493$ |

Впятеро по деньгам. Корреляция на поздних годах даже сильнее: −0.76 против
−0.64 на ранних. Это единственный результат проекта, который выжил на
отложенных данных и стал сильнее. Оговорка: в хорошей корзине всего
7 конкурсов.

Заодно объясняется, почему рынок испортился: **медианная плотность выросла
с 0.115 до 0.361, втрое.** Толпа не просто выросла в числе — она стала
плотнее покрывать код, и только 7 конкурсов из 43 за 2025–2026 остались
ниже старой медианы.

Встроено в `contests.py` (сортировка по плотности) и `scout/rank.py`
(`density_outlook`, `min_scope`). При базовой ставке ~200 заявок тонкое
покрытие начинается со скоупа примерно в 4000 строк.

`python protocols.py --type <тип>` печатает характерные для типа слова
заголовков (счёт по конкурсам, не по находкам) и дорогие одиночные находки
дословно.

Оговорка по методу: классификатор первой версии сваливал 128 конкурсов из 235
в «стейкинг», потому что слова `reward`, `lock`, `deposit` есть в любом
протоколе. Приметы ужесточены до специфичных. У типов с 4–5 конкурсами
статистика слов не работает — там смотреть надо сами находки.

## Вывод

**Фаза 0 работает** и даёт настоящие числа для решения, куда идти.
**Фаза 3 работает** и отвечает, на что смотреть.
**Фаза 1 работает на уровне функций** и не работает на уровне файлов.

Экономика: медиана 38$ за заявку в 2026, но валидная High стоит 639$, Medium
388$, и почти треть из них нашёл один человек. Это не автоматизируемый доход
и не «сканер печатает деньги» — это профессия, где инструмент экономит время
на разведке, а находит человек.

Практическое правило, вытекающее из всего измеренного:

1. Конкурс выбирать по `contests.py`, а не по размеру фонда — фонд не
   предсказывает тесноту вообще.
2. Читать начинать с беспермиссионных функций, двигающих деньги: 5% кода,
   тройная плотность находок.
3. Функции с `onlyOwner` пропускать — лифт 0.53, посторонний туда не дотянется.
4. Классы, которые ловит автоматика (нестандартные токены, контроль доступа,
   инициализация), не подавать: 27% одиночек и 170–468$ медианы. Их найдут и
   без тебя, а награда делится на всех нашедших.

## Файлы

- `scout/http.py` — клиент с дисковым кэшом
- `scout/model.py` — единая запись конкурса, метрики тесноты
- `scout/sherlock.py` — список, детали, отчёты; язык по расширениям в scope
- `scout/cantina.py` — список соревнований
- `scout/rank.py` — базовая ставка года; там же документирована неудавшаяся регрессия
- `scout/recon.py` — разбор кода; в шапке результат проверки ранжирования
- `scout/corpus.py` — разбор отчётов, классы находок; работает офлайн
- `contests.py` — фаза 0, выбор конкурса
- `recon.py` — фаза 1, карта репозитория
- `corpus.py` — фаза 3, корпус находок
- `validate.py` — проверка инструмента против реальности, офлайн
- `prefetch.py` — массовая закачка с докачкой, под слабый канал

## Под слабый интернет

```
python prefetch.py --status              что уже есть
python prefetch.py --cards               карточки конкурсов (~20 МБ)
python prefetch.py --repos --limit 40    репозитории пачкой, по одному
```

Прерванный запуск продолжается с того же места: состояние в
`data/prefetch.json`, скачанное не качается повторно. После закачки
`validate.py` и `corpus.py` работают офлайн.
